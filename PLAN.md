# TagMails — product and build plan

- Date: 2026-10-02
- Status: Gmail-style lab, localhost Rust worker, and account-routed relay ingress prototype implemented; a private TagMails Site hosts the landing preview, while live email delivery has not started
- Public brand: TagMails
- Internal project name: Wonder Email

## Product promise

Give an existing local agent an email address. A customer signs in with Google, connects Codex or Claude Code on their computer with one copyable setup prompt, and sends work to the address. The service queues the message while the computer is offline. The local daemon resumes the appropriate agent session, completes the task, and sends a concise result in the same email thread with artifacts and a private run link. A reply continues that session. The daemon, relay, account site, and viewer are open source. The managed deployment charges for email delivery and retained storage; optional API-funded execution uses credits.

The initial audience is people already using coding agents who want to assign a task from any email client. The first supported agent runtimes are Codex and Claude Code. The first platform for the daemon is macOS. The website handles account setup, balance, address and device status, memory controls, traces, and billing; routine work stays in email.

## Journey and boundaries

1. Sign in with Google. For the first beta, accept a verified `@gmail.com` address and make it the initial authorized sender; defer Google Workspace and other Google-account addresses until sender verification is designed for them. Save Google's stable `sub` as account identity. Google sign-in does not need Gmail mailbox access. [Google OIDC](https://developers.google.com/identity/openid-connect/openid-connect)
2. Reserve `name@tagmails.com` once that domain is acquired and verified, choose a workspace and local runtime, and copy the Codex or Claude Code setup prompt. The installer pairs a device, registers a macOS LaunchAgent, and tests a read-only status call.
3. Send a task from the authorized address. The relay verifies the email provider's signed webhook, records one durable job per incoming message, checks sender authorization, and gives the local daemon a signed job envelope. The daemon only pulls outbound over HTTPS.
4. A new email creates a project session. A reply resolved through `Message-ID`, `In-Reply-To`, and `References` continues the saved session. Subject lines are display text, not session identity. [Resend threading](https://resend.com/changelog/message-id-for-sent-emails)
5. The completion email contains a clear outcome, what changed or was delivered, checks and limitations, action links, small attachments when appropriate, a private trace link, and a simple invitation to reply. Failed or waiting runs say what needs attention. The full trace stays inspectable outside the email.
6. The owner grants thread-scoped participation by including another address in To or Cc on an email to the agent. The local lab also simulates Bcc grants when it knows the sender's complete recipient list. Gmail hides other Bcc guests from the copy delivered to the agent. The account page now has an explicit owner grant for a Bcc address on an existing thread; automatic Bcc grants would require verified owner Gmail Sent access. Only the owner can add participants and revoke access. A participant cannot expand workspace or action permissions. Bcc recipients remain hidden from visible reply headers; their replies are private unless they explicitly include the owner. Production must authenticate the owner and verify inbound sender provenance before treating a recipient field as a grant.

### Default safety rules

- The Google-verified sender is authorized for ordinary tasks within the configured workspaces. A new address is added through an authenticated account action or a verified invitation. SPF/DKIM/DMARC results are defense in depth; the visible `From` field alone is insufficient.
- Forwarded mail, quoted text, attachments, web pages, and repository files are task data. They do not change permissions or billing limits.
- Separate local approval remains required for sensitive side effects such as sending mail as the user, merging, deployment, purchases, or broad file access. The service's signed envelope does not override the runtime's approval boundary.
- A selected `workspaceWrite` root alone does not restrict reads. The Codex lab and relay adapter now use a dedicated app-server runtime home and an explicit `tagmails-read` profile: reads in the selected workspace, no writes, no outside reads, no command network, and no Codex web search. Before a turn, the adapter verifies that app-server activated that profile, repository settings are untrusted, and external tools are absent; it declines permission-expansion requests. Direct sandbox checks blocked workspace writes, outside reads, a symlink escape, and Codex auth reads. A real Luna scratch session read a note and resumed on the next turn; a separate turn read a staged attachment and cleaned it up. This remains a local boundary test, with production runtime approvals still to design. [Codex permission profiles](https://learn.chatgpt.com/docs/permissions)
- The first write-capable local path is now an opt-in `tagmails-write` profile for one selected folder, with workspace writes, no command network, and `on-request` approval for attempts beyond the boundary. Runtime auth and the session store stay outside that folder. TagMails declines permission expansion and records a waiting result; the lab cannot treat its mock approval button as approval for a real agent request. A disposable sandbox check allowed an inside write and denied outside reads and writes, a symlink escape, and auth access. Real Luna created a file, resumed the same session to append to it, then completed a separate synthetic email through the Rust worker and rendered a threaded result. The paired relay now selects this adapter only when the Mac owner explicitly configures local write access; a customer approval flow remains to be built. [Codex sandboxing](https://learn.chatgpt.com/docs/sandboxing) · [app-server approvals](https://learn.chatgpt.com/docs/app-server)
- Claude has a separate opt-in `claude-write` local lab mode using the installed subscription CLI in restricted mode with Read/Glob/Grep/Edit/Write only, `acceptEdits`, no command or web tools, and a session store outside the selected workspace. A real Sonnet scratch session created a file and resumed to extend it; a separate synthetic email passed through the Rust worker and rendered the write result in the Gmail-style thread. Direct restricted-mode probes denied a Write outside the workspace and a Read through a symlink to an outside file. A CLI boundary denial is now labeled as needing local access review, even when Claude reports a successful turn; the mock approval button cannot approve it. A failed turn may leave partial edits. The paired relay selects this adapter only through the Mac's local write setting; production approval flow remains. [Claude CLI reference](https://code.claude.com/docs/en/cli-reference) · [Claude permissions](https://code.claude.com/docs/en/permissions)
- The paired relay now reads a local `TAGMAILS_WORKSPACE_ACCESS` setting, defaulting to `read`. An explicit `write` switches signed jobs to the bounded Codex or Claude workspace-write adapter; the remote claim cannot widen the selected folder or change that setting. The macOS installer and private Site setup page expose this choice, with read-only selected first. A disposable run through signed synthetic Resend webhooks, fixture-retrieved raw MIME, the in-process relay handler, and the Rust daemon selected Codex write: a real Luna owner turn created `proof.txt`, then an owner-authorized Cc participant replied in the same thread and added a second line. The local D1 fixture recorded two completed jobs; a local provider stub accepted both replies. The guest turn referenced the first sent Message-ID, and the second reply preserved the ordered `References` chain. Two scratch runs completed without the requested file; one falsely said it had created it. Codex and Claude write prompts now require reading changed files back before claiming success, and the next Luna smoke passed, but runtime reliability still needs pilot measurement. Each write adapter now saves an uncertain-result record before starting a turn; simulated process interruptions left a scratch edit, and reusing the same email job ID returned a failure rather than executing another edit. This protection depends on the same local session store and does not verify the edit. Completed result mail says “Agent reply” and marks write-turn edits as the agent's report, with an explicit request to verify local changes. This is a local pilot permission; production approval and incident recovery still need work before unattended customer use.
- Deduplicate provider webhooks and mail `Message-ID`s. Persist job state before acknowledging inbound mail. An interrupted job checks its prior side effects before retrying. A completion message is sent once.
- Keep local model credentials on the user's computer. Keep service API secrets in the managed server's secret store. Store traces and artifacts privately with scoped, expiring access.

## Architecture to implement first

```text
Google account ── signup ──▶ open-source web/relay service
                                   │
incoming email ── Resend webhook ──┼──▶ durable jobs + credit ledger (D1)
                                   │                 │
                                   │             encrypted payloads,
                                   │             traces and files (R2)
                                   ▼
                      signed job claim over HTTPS
                                   ▼
                    Rust daemon on the customer's Mac
                    ├── local SQLite identity, memory, sessions
                    ├── Codex app-server adapter
                    └── Claude Code/Agent SDK adapter
                                   │
                         result + artifact manifest
                                   ▼
                           threaded email reply
```

**Proposed managed stack:** one TypeScript Cloudflare Worker for auth, address reservation, Resend webhooks, job claims, account pages, trace access, and Stripe webhooks; D1 for transactional metadata and an append-only credit ledger; R2 for bounded email payloads, attachments, traces, and artifacts. No Durable Object is required for the first job queue. Cloudflare currently lists a $5/month minimum for Workers Paid, with 10 million requests and 30 million CPU milliseconds included; D1 Paid includes 25 billion rows read, 50 million rows written, and 5 GB storage. [Workers pricing](https://developers.cloudflare.com/workers/platform/pricing/) · [D1 pricing](https://developers.cloudflare.com/d1/platform/pricing/)

**Self-hosting contract:** the same open-source server can be deployed to a separate Cloudflare account with its own domain, Resend key, D1, and R2; billing can be disabled. Document this path and test it before claiming self-hosting support. Additional mail and storage providers are later adapters once the first provider is stable. MIT is the selected source license, matching Wonder and T3 Code; retain original copyright notices if substantial code is reused. The source is not publicly released yet.

A [self-hosting starter](SELF_HOSTING.md) now documents a separate Worker, D1, R2, Google sign-in, Resend, and a no-billing/no-Site path. Its Wrangler config bundled in a local dry run and the receipt fallback has a focused test. A fresh Cloudflare-account deployment and actual inbound-to-outbound email remain required before self-hosting can be advertised as supported.

**Run transcript link:** Owner-addressed results link to a run page on the TagMails ChatGPT Site when `SITE_ORIGIN` is configured, using the run UUID in the URL. The UUID identifies the run; it does not authorize access. The Site uses Google sign-in and asks the relay for that run under the signed-in identity. The relay grants the owner full access, or an active Gmail participant transcript-only access when that person appears in the saved reply's To/Cc list. Participant responses exclude artifacts and other recipients' delivery statuses. The Site currently permits only the owner to visit, so guest-only email links remain disabled; after an approved audience change and live guest sign-in check, `SITE_PARTICIPANT_TRANSCRIPTS=true` can enable them. Codex and Claude capture actual user-visible messages, tool steps, and final answers as a normalized event stream, with explicit truncation. Credentials, hidden reasoning, raw tool output, and system prompts are excluded. The Site's Google origin was authorized, the owner's Gmail sign-in opened a seeded dev fixture containing a genuine Luna scratch-run result from remote D1/R2, and cross-account and revoked-guest API denial passed local tests. No email has delivered the link yet. The Worker's authenticated receipt remains a fallback when no Site origin is set.

**File transfer:** Keep the public run page as simple responsive HTML. The relay source now accepts at most five inbound files, 24,000,000 bytes each and 25,000,000 bytes combined within a 38,000,000-byte encoded MIME allowance. Signed claims carry metadata and lease-bound download paths; the paired device fetches each file with its token and verifies the byte count. A 24 MB synthetic MIME passed local claim, download, completion, and reply rendering tests. The localhost lab retains its 5 MiB raw/3 MiB attachment limits. The dev relay also accepts up to five output files from a paired device's active job lease (24,000,000 bytes each; 25,000,000 total), stores them privately in R2, and presents only completion-selected files to the account owner on the Site and Worker receipt. The seven-day output file deletion job is deployed. Raw inbound MIME is also removed after seven days once the job and reply are settled or blocked, while message IDs remain for thread routing. Queued and uncertain deliveries retain their MIME for recovery; define a separate timeout and operator process before launch. The owner's Gmail sign-in downloaded a seeded synthetic fixture from the Site and its bytes matched the R2 source. A verified owner can request the answer as `answer.txt`, or one specific existing workspace file using a first-line `TagMails-File: relative/path` directive. A write-enabled agent can generate the file; the daemon validates its path and size before upload. Separate local signed-claim smokes with real Luna turns exported the answer and exact bytes of a newly created file, then queued replies; no real email was sent. Read-only runners can export existing files but cannot create them. Participant downloads are not yet authorized, and live Resend delivery and Worker memory at the 24 MB boundary remain unverified. Do not advertise general file transfer until those gates pass. A larger-file Google Drive option would require a *separate, optional* Drive consent from Google sign-in. Use the narrow `drive.file` scope for app-created files, resumable uploads, explicit recipient sharing, a recorded expiry, and a deletion job that retries failures and checks removal after seven days. Do not make a Drive file public merely because the email thread has participants. [Gmail attachment guidance](https://support.google.com/mail/answer/6584) · [Drive file scope](https://developers.google.com/workspace/drive/api/guides/api-specific-auth) · [resumable uploads](https://developers.google.com/workspace/drive/api/guides/manage-uploads) · [Drive deletion](https://developers.google.com/workspace/drive/api/guides/delete)

**Daemon:** Rust owns pairing, device keys, queue polling, local persistence, launch-at-login, workspace boundaries, and recovery. Keep runtime-specific protocol handling in small adapters. Inspect Wonder's App Server item projection and reconciliation (`crates/wonderd/src/history.rs`, `crates/wonderd/src/lib.rs`), its `crates/wonder-app-server`, and `services/claude-runtime` before copying logic. Review T3 Code's transcript and projection paths for ideas and license terms; its repository is MIT licensed. [T3 Code](https://github.com/pingdotgg/t3code)

## Email output and research loop

Create a versioned response specification and fixture corpus before tuning prompts. The renderer takes a structured run result, so the agent does not improvise raw HTML or unverified links. Each email has a plain-text part and a conservative HTML part. Use semantic headings, paragraphs, lists, clear links, descriptive image alt text, and small inline previews when tested. Keep large files and videos behind private web links with an image poster and a plain text fallback. Gmail's 25 MB attachment limit applies to personal accounts, and Gmail's automatic Drive conversion is for a user attaching files in Gmail; the relay must host oversized files itself. [Gmail attachment guidance](https://support.google.com/mail/answer/6584)

The internal test site will mimic a Gmail conversation list and thread view while rendering **the actual generated MIME** and status events from a local fixture relay. It will support sample inbound messages, multi-person replies, To/Cc/Bcc participation, model overrides, offline queueing, approvals, attachment previews, Gmail reactions, and failure states. It is an inspection tool, not a public Gmail clone.

For a Gmail-first experience, send directly from the agent address in a normal threaded email with the intended participants in To/Cc, at most 20 recipients, and no custom Reply-To. Gmail can show its native emoji reaction control on that message when the recipient opens it in a supported Gmail client; a Gmail address alone does not prove which client they use. A reaction arrives as a MIME email with a `text/vnd.google.email-reaction+json` part and an `In-Reply-To` pointing to the reacted message; record it as feedback without starting an agent run or charging for a task. Gmail does not offer reactions to Bcc recipients on that message. The development `onboarding@resend.dev` sender needs a custom Reply-To for the agent alias, so it cannot verify the native reaction control; use a verified sending domain for that live test. The shared inbound parser accepts Gmail's valid nested `multipart/related` reaction format with an inline file, which a local reaction fixture now covers. [Gmail reaction format](https://developers.google.com/workspace/gmail/reactions/format) · [Gmail reaction limits](https://support.google.com/mail/answer/14080429?co=GENIE.Platform%3DDesktop&hl=en)

Use [Claude Tag's published examples](https://www.anthropic.com/news/introducing-claude-tag) as a product-behavior reference: people hand an agent a messy existing conversation, ask for a catch-up or a concrete artifact, and come back to the same thread after it works asynchronously. The first synthetic email fixtures should feel like a decision catch-up, an incident or bug report leading toward a draft PR, a metrics question, and a follow-up that needs a person's decision. Keep memory and access scoped to the email thread and configured workspace. Future scheduled or proactive work can follow after direct email tasks are reliable; the examples must never imply a mock run actually changed code or queried live data.

Run an iterative evaluation loop on a fixed fixture set: code change with PR, report with citations, image output, video output, attachment input, ambiguous model request, multi-person thread, offline/retry, approval request, and failed run. Score factual fidelity to the run, action and link validity, scanability, reply continuity, accessibility, and client rendering. Compare prompt versions in the mock inbox, then send a small set of real Gmail↔agent-address messages with Luna and inspect Gmail desktop and mobile behavior. Save the exact MIME, screenshots, costs, and failures. Promote a prompt only when it improves the fixtures without regressions.
